# 智能运维问答助手（RAG）

一个**不需要 API key 就能直接跑**的中文运维问答 Demo：本地 TF-IDF 检索运维知识库 + 模板化/LLM 生成回答，并自带 Hit@1 / Hit@3 检索评测。

## 背景

一线运维每天被同一批问题反复打断：nginx 又 502 了、磁盘又满了、慢查询又来了。这类问题的答案往往早就沉淀在团队的 wiki / 值班手册里，真正麻烦的是**在故障现场快速找到那一条**——靠记忆翻文档、或者 `grep` 整个目录，都比故障本身更耗时。

这个项目把「知识库 → 检索 → 生成」这条 RAG 链路做成一个可运行的最小实现，重点不是堆技术栈，而是把工程取舍和**真实的评测数字**摆出来：

- 默认**纯离线**：本地检索 + 模板拼装，克隆下来 `python src/main.py --query "..."` 就能跑，不联网、不要 key；
- 想接大模型时，设三个环境变量即走 LLM 分支，失败自动回退离线模式；
- 配了 10 条评测问题，`--eval` 会打印 Hit@1 / Hit@3 并生成 Markdown 报告。

知识库 28 条、检索零依赖（只要 numpy），是刻意做小的：**能被人一眼看懂的规模，才方便面试时追问细节。**

## 架构

```
                    data/kb.jsonl  （28 条运维条目，JSON Lines）
                            │  逐行 json.loads，坏行带行号报错
                            ▼
┌─────────────────────── src/retriever.py ───────────────────────┐
│  分词     汉字 → 字符 bigram（"磁盘满了" → 磁盘/盘满/满了）        │
│           英文数字 → 整词（nginx、502、proxy_read_timeout）       │
│           停用词过滤（怎么/什么/如何…，这些词对区分文档没贡献）     │
│  建索引   TF 词频 × IDF（log((1+N)/(1+df)) + 1）                │
│           字段加权：标题、标签 ×2（类似 BM25F 的字段加权）        │
│           逐行 L2 归一化                                        │
│  检索     cosine(query, doc) = doc_matrix @ query_vec           │
│           排序取 top-k，相似度为 0 的不返回                      │
└──────────────────────────────┬─────────────────────────────────┘
                               │  [(doc, score), ...]
                               ▼
┌─────────────────────── src/generator.py ───────────────────────┐
│  ① 离线模式（默认）                                              │
│     top1 的 answer 作正文 + prompts/answer_template.md 拼装      │
│     末尾「参考」列出 top3 标题与相似度                            │
│  ② LLM 模式（设了 LLM_API_KEY 才走）                             │
│     prompts/system_prompt.md 作 system                          │
│     top3 片段按 [1][2][3] 编号塞进 user message                  │
│     POST {LLM_BASE_URL}/chat/completions（urllib，30s 超时）     │
│     任何异常 → stderr 告警 → 自动回退 ①                          │
└──────────────────────────────┬─────────────────────────────────┘
                               ▼
                    src/main.py  CLI
        --query "..."  │  --eval  │  --interactive
                               ▼
              stdout（答案）+ reports/eval_report.md（评测）
```

## 两种运行模式

| | 离线检索模式（默认） | LLM 生成模式 |
| --- | --- | --- |
| 触发条件 | 不设任何环境变量 | 设了 `LLM_API_KEY` |
| 需要什么 | 只要 numpy | API key + 可访问的 OpenAI 兼容接口 |
| 是否联网 | 不联网 | 会请求 `/chat/completions` |
| 回答来源 | top1 文档的 `answer` 原文 | 模型基于 top3 片段生成的文本 |
| 失败时 | — | 打印告警，**自动回退离线模式**，退出码仍为 0 |
| 本机验证情况 | ✅ 已跑通 | ⚠️ 未做真实调用验证（开发机无 key），仅验证了异常兜底 |

切换 LLM 模式（三个变量，只有 key 是必填）：

```bash
# Linux / macOS
export LLM_API_KEY="sk-xxxx"
export LLM_BASE_URL="https://api.openai.com/v1"   # 可选，默认就是这个
export LLM_MODEL="gpt-4o-mini"                    # 可选，默认就是这个
```

```powershell
# Windows PowerShell
$env:LLM_API_KEY="sk-xxxx"
```

> LLM 分支需要自备 API key，本仓库默认离线模式；LLM 分支代码**未在本机验证**（无 key）。
> 已做的验证只有：把 `LLM_BASE_URL` 指向本机不可达端口，确认程序打出告警、回退离线模式、且退出码为 0。
> 真实的 200 响应解析路径没有跑过，第一次接真实服务时建议先 `--query` 单条试。

## 怎么跑

```bash
# 1. 安装依赖（离线检索只要 numpy）
pip install -r requirements.txt

# 2. 单次问答
python src/main.py --query "nginx 502 怎么排查"

# 3. 跑评测，生成 reports/eval_report.md
python src/main.py --eval

# 4. 交互式问答，输入 exit 退出
python src/main.py --interactive

# 5. 不带参数 = 打印帮助
python src/main.py
```

```
### 问题

nginx 502 怎么排查

### 回答

502 表示 nginx 作为反向代理时上游（upstream）不可用或返回了非法响应，按下面顺序查：
1. 先看错误日志，确认是 connection refused 还是 upstream 提前关闭：`tail -n 200 /var/log/nginx/error.log | grep -i upstream`
2. 确认上游进程是否在监听：`ss -lntp | grep 8080`，没有监听就是后端挂了，先把服务拉起来。
3. 绕开 nginx 直连上游验证：`curl -v http://192.0.2.10:8080/health`，看是拒绝连接还是返回 5xx。
4. 看上游应用日志：有没有崩溃、Full GC、连接池耗尽、线程池打满。
5. 检查 proxy_connect_timeout / proxy_read_timeout 与 keepalive 配置，上游处理慢会同时表现为 502 和 504。
6. 如果后端是 PHP-FPM，确认 worker 数与 pm.max_children 是否被打满（`ps -ef | grep php-fpm | wc -l`）。

### 参考

1. **nginx 502 Bad Gateway 排查**（`kb001`，相似度 0.453）
2. **nginx 静态资源 404**（`kb027`，相似度 0.173）
3. **nginx 504 Gateway Timeout 排查**（`kb002`，相似度 0.162）
====================================================================
```

**这个 100% 需要打折看，说明如下（重要）：**

1. 评测集是我自己照着这份知识库写的，问法和条目用词有重叠（"nginx 502"、"OOM killer"、"8080 端口"这类强特征词直接命中），所以 100% 只说明**链路是通的、目标文档能被正确排到第一**，不代表对任意用户问法的泛化能力。真实场景要用人写的、独立于知识库的评测集。
2. 换一种同样自然的问法就会掉下来，下面这条是真实跑出来的失败案例（只摘录检索表部分，`<-` 是我的批注）：

```
$ python src/main.py --query "磁盘满了怎么办"
  1  kb028       0.220  binlog 堆积导致磁盘满     <- 应该是通用磁盘清理（kb003）
  2  kb015       0.176  磁盘 IO 使用率过高
  3  kb003       0.119  服务器磁盘空间满的清理方法
```

原因很具体：查询里的 bigram 是 `磁盘 / 盘满 / 满了`，而 kb003 的标题写的是"磁盘**空间**满"，只能对上 `磁盘`；
kb028 的标题和正文同时含 `磁盘` 和 `盘满`，两个 bigram 都命中就赢了。换成 `"磁盘空间满了怎么清理"` 则 kb003 正常回到第一（0.351）。
这正是字符 bigram 的典型失效模式——**只认字面重合，不认同义**。

## 技术栈

- **Python 3.10+**（用了 `str | None` 之类的新语法），**numpy** 做向量运算，其余全部标准库
- 检索：字符级 bigram + 英文数字整词、TF-IDF（平滑 IDF `log((1+N)/(1+df))+1`）、L2 归一化、余弦相似度、标题/标签字段加权、停用词过滤
- 生成：Markdown 模板占位符替换（`{{query}}` / `{{answer}}` / `{{references}}` / `{{mode}}`）；LLM 分支用 `urllib.request` 手写 OpenAI 兼容调用
- 评测：Hit@1 / Hit@3 + 自动生成 Markdown 报告
- 没有 langchain / openai / faiss / sklearn / jieba —— 检索部分全部手写，方便逐行讲清楚

## 局限

- **知识库只有 28 条**，覆盖的是最常见场景；问法稍偏或场景更细（比如"k8s ingress 502"）就检索不到，会直接返回空结果而不是瞎编。
- **字符 bigram 的语义能力有限**：只认字面重合，同义词（"磁盘满" vs "空间不足"）、缩写、错别字都处理不了，具体失败案例见上一节。
- **没有做 rerank**：top3 直接按 TF-IDF 余弦排序，没有交叉编码器或规则重排，所以 top2/top3 里常混进弱相关条目（例如问 nginx 502 时冒出 nginx 404）。
- **离线答案不是"生成"的**：直接引用 top1 的 `answer` 原文，问法和条目措辞不一致时会显得答非所问；它的价值是**零幻觉**，代价是灵活性。
- **LLM 分支未在本机验证**：没有 API key，真实的请求/响应链路没跑过，只验证了"失败必定回退离线模式"。用之前请先用单条 `--query` 试通。
- **评测量只有 10 条且自拟**，统计意义有限（10 条里错 1 条就是 10 个百分点），只能当回归冒烟测试用。
- 检索是**单轮**的，不记得上下文，也不支持追问；没有做权限隔离，知识库里不应放任何敏感信息（示例统一使用 `192.0.2.x` 这类文档保留地址）。
